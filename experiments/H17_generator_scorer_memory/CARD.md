# H17 · A memory read by both the generator and the scorer, trained with them, picks better paths

**Siddesh** · offline, AlpaSim · 🗑 dropped · 7 Nov – 20 Nov 2026 · hypothesis

[← all experiments](../../README.md#hypothesis-experiments) · [the account](README.md) · [experiment.toml](experiment.toml)

**Builds on:** [H05](../H05_ssm_memory/CARD.md), [H19](../H19_prediction_memory/CARD.md) · **Evidence for:** D21 ([decision log](../README.md#decision-log))

## Question

H05 found that the camera's past, read through a small probe, adds little; H19 carried only the planner's own outputs and could not be told from the same layer wiped. Both left the released model frozen. Does a memory help when the two parts that decide the drive, the generator that proposes 32 paths and the scorer that picks one, are trained to use it?

## Hypothesis

A memory of 16 slots, written at every moment from the frozen encoder's output and read by both the generator and the scorer, trained together with them from Drive-JEPA 0.1.8b on Physical AI AV, makes the scorer pick better paths than the same model with the memory wiped at every moment. Expected: a higher mean grade of the picked path on the picking set, and at least +0.01 on moments within 5 s after a cut-in, a crossing or a hard brake. Refuted if the carried memory does not beat the wiped one.

## Predictions

⚠️ Not pre-registered: the rule for each run was written before it started (file times and run logs agree) but in a folder outside git, so no commit date shows it

## What we learned

Camera memory gave no gain in closed loop over 50 scenes: 0.7464 against the starting model's 0.7574 on AlpaSim's scene score, one drive per scene. Its early lead came from the 12 scenes that had been looked at first (+0.129 there); on the 18 others it was +0.027, and on 20 scenes never looked at before it was -0.129, against by the rule written beforehand, with two at-fault crashes inside the score window that the starting model does not have. The memory car drifted 4 m from the human path sooner, on 16 of those 20 scenes. The car's own motion history is the stronger signal (the next experiment). Offline the picture was the same: camera memory has a low ceiling on this data, as far as a linear reader of pooled camera views can see. With a healthy memory (slots distinct, gates open, earlier views recalled), carrying it gave a pick grade of 0.7313 against 0.7355 with the same weights and the memory reset every moment, on 1,131 graded moments (-0.0042, 95 % interval -0.0103 to +0.0012): no gain. The first training run's gap in favour of the carried memory (0.7752 against 0.7639, interval -0.008 to +0.032) came with a collapsed memory whose 16 slots were 99.96 % alike; that the gap is not the memory working as designed is argued, and that model did lean on what the memory held (zeroed at test time: 0.7662, and the pull-away go rate 74.5 % -> 39.6 %). A linear test found the trained memory adds nothing linearly readable for predicting the driver beyond the current view and the car's own motion history. Given the true past camera view directly, a linear reader gains 1 to 2 % on speed on all moments and up to 3.9 % (2.1 to 5.5) on moments after an event, and nothing on braking or steering; by its rule written beforehand that is unclear, and no non-linear reader was shown to do better. The car's own motion history is the stronger signal, and is a separate, later experiment. Limits: one seed, one data set; one drive per scene; the closed-loop comparison is two models, so the memory is not separated from the 930 extra training steps that came with it.

## Checks that decided something

- **Was the memory in the first training run working?** (10 Nov): No. At the carried arm's chosen check the 16 slots were 99.96 % alike (mean pairwise cosine 0.9996) and the gates were almost shut (mean 0.006 per slot). → fix the memory before reading anything from the gap between the arms (H17.collapse-fix, H17.recall-lesson)
- **Does the trained memory hold information that matters for driving?** (12 Nov): No, by the rule written beforehand, for a linear reader: adding the carried memory predicts the driver's next 3 s no better than adding the wiped memory on any of six targets; both controls pass. On top of the current view and the car's own history it adds -2.8 % to +0.6 %. The rule file limits this to what is linearly readable. → ask whether the true past camera view helps at all
- **Does the true past camera view help predict the driver?** (12 Nov): Unclear, by the rule written beforehand. Views from 2 s and 4 s ago add at most 1.2 to 1.3 % on speed at +3 s (bar 2 %) and 1.7 % on event moments (bar 5 %); the view from 2 s ago alone adds 3.9 % [2.1, 5.5] on event moments at +3 s, the largest gain found; the linear reader's gains on speed exclude zero; nothing on braking or steering. The small network reader gained nothing even with the true past view, so it bounds nothing. → park the camera memory; the car's own motion history is a separate experiment
- **Does the simulator, rebuilt, drive the same as before?** (20 Nov): Yes, twice. After a rebuild on 12 Nov, 4 of the starting model's drives of 31 Oct gave the same scores and bit-identical per-tick metrics. After a second rebuild on 20 Nov, 6 earlier drives (4 of the starting model, 2 of the memory model) did the same. → pool drives made on the three simulator builds
- **12 scenes in closed loop, memory carried against memory reset** (13 Nov): Carried 0.7213, reset 0.5177, the starting model 0.5919, one drive per scene. By its rule written beforehand the memory helps in closed loop. These are the scenes the earlier diagnosis studied, so they were looked at before the memory ran. → drive the other 18 scenes of the 30 against the starting model
- **18 more scenes: memory carried against the starting model** (14 Nov): Carried 0.8865, the starting model 0.8599: +0.027, 3 wins, 0 losses. By its rule written beforehand, it hurts: two at-fault crashes the starting model does not have, both after the score window had closed (the rule counted a crash at any time). → drive 20 scenes neither model had been tested on
- **Rescore every drive to its last tick** (17 Nov): Withdrawn. The re-score read crashes beyond 4 m from the recorded path, where the renderer is not valid, so its numbers are not used. The report and scripts are kept as they ran. → keep the standard score, which stops at 4 m
- **One of the 20 new scenes could not be driven** (20 Nov): Scene 9e6753c2 stopped the simulator 12 s in, three times, on a fault in its map (the route folds back on itself). It was replaced by 44409f00, the first of the same pool in a shuffle with seed 0, by a rule written before the draw. The starting model was never driven on 9e6753c2.
